CQS - Command/Query Separation

Part 1: Foundationsprinciple

Definition

Command-Query Separation says an operation should either change observable state or return information, but not do both in a surprising way. Queries are safe to repeat and reason about; commands make effects explicit.

The principle is about semantic clarity, not a prohibition on every method returning a status. If a command returns an acknowledgement needed to know whether the command succeeded, that contract should be explicit.

Problem It Solves

A method that looks like a getter but lazily mutates state, sends a request, or updates a cache makes repeated calls unpredictable and complicates tests, retries, and concurrency.

C++ Before

bool hasItem(const Item& item) {
  if (!loaded) loadFromNetwork(); // hidden command
  return items.contains(item);
}

C++ After

void load() { items = repository.fetch(); loaded = true; }
bool contains(const Item& item) const {
  return items.contains(item); // pure query
}

load();
if (cart.contains(item)) { /* ... */ }

Trade-offs and Misuse

  • Separating operations can require an explicit workflow at the call site.
  • Do not pretend caches and lazy loading are free of effects; name or document them.
  • CQS improves retry and concurrency reasoning, especially at service boundaries.

Relationships

CQS is related to CQRS, functional programming, idempotency, and explicit side-effect boundaries.
