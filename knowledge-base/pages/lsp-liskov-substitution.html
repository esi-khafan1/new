LSP - Liskov Substitution

Part 1: Foundationsprinciple

Definition

The Liskov Substitution Principle requires a subtype to honor the behavioral contract of its base abstraction. Code using the base type must continue to work when given a valid subtype, without type checks, surprise exceptions, or weakened guarantees.

Substitutability covers preconditions, postconditions, invariants, error behavior, and meaningful semantics. Matching method signatures is not enough.

Problem It Solves

Bad inheritance makes callers defend themselves with casts and special cases. The hierarchy then advertises a promise the subtype cannot keep.

C++ Before

void resize(Rectangle& r) {
  r.setWidth(5); r.setHeight(10);
  assert(r.area() == 50);
}
// Square changes both dimensions in either setter.

C++ After

struct Shape {
  virtual ~Shape() = default;
  virtual int area() const = 0;
};
class Square : public Shape {
  int side;
public:
  explicit Square(int s) : side(s) {}
  int area() const override { return side * side; }
};

The abstraction promises area, which both shapes can honor. It does not pretend every shape supports rectangle mutation.

Trade-offs and Misuse

  • Prefer a smaller interface or composition when inheritance requires exceptions.
  • Do not weaken a base contract merely to make a subtype fit.
  • Tests should exercise the same client scenarios against every subtype.

Relationships

LSP is the behavioral foundation of OCP and safe polymorphism. ISP helps create contracts that subtypes can actually satisfy.
