OCP - Open/Closed

Part 1: Foundationsprinciple

Definition

The Open/Closed Principle says software should be open for extension but closed for modification. Stable policy should not need edits every time a new variant of volatile behavior appears.

This is not a ban on changing code. It is a design question: where can variation be added without reopening trusted logic? Useful extension points include polymorphism, composition, registration, and data-driven rules.

Problem It Solves

A growing switch statement makes every new payment method, report format, or discount rule modify the same class. The class becomes a hotspot where unrelated features collide and old behavior is easy to break.

C++ Before

void charge(std::string kind, int cents) {
  if (kind == "card") cardCharge(cents);
  else if (kind == "bank") bankCharge(cents);
  else if (kind == "wallet") walletCharge(cents);
}

C++ After

struct PaymentMethod {
  virtual ~PaymentMethod() = default;
  virtual void charge(int cents) = 0;
};
class Processor {
public: void charge(PaymentMethod& method, int cents) { method.charge(cents); }
};
class CardPayment : public PaymentMethod {
public: void charge(int cents) override { /* card gateway */ }
};

Adding a new method adds a type. The processor remains closed to that variation.

Trade-offs and Misuse

  • Abstractions added before variation is real become speculative complexity.
  • A conditional is fine when the variants are stable and local.
  • Extension points must preserve a meaningful contract, or OCP becomes an escape hatch for duplication.

Relationships

OCP depends on abstraction, composition, LSP, and dependency inversion. Strategy, Factory, and Decorator are common implementation tools.
