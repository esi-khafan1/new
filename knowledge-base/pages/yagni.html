YAGNI - You Aren't Gonna Need It

Part 1: Foundationsprinciple

Definition

YAGNI says do not implement a capability until a current requirement demands it. Future features are uncertain: building them early spends design, test, documentation, and maintenance budget before their shape is known.

YAGNI does not reject good design. It rejects speculative behavior, unused extension points, and configuration knobs whose only justification is that someone might need them later.

Problem It Solves

Speculative features create dead code and constrain future decisions. An imagined plugin system may be harder to replace than a small direct implementation once the real requirements arrive.

C++ Before

class Report {
  std::map<std::string, std::any> futureOptions;
  std::vector<Plugin> plugins;
  // No current requirement uses either feature.
};

C++ After

class Report {
  std::vector<Row> rows;
public:
  explicit Report(std::vector<Row> data) : rows(std::move(data)) {}
  const auto& data() const { return rows; }
};
// Add extension only when a concrete second use case exists.

Trade-offs and Misuse

  • Avoiding all preparation can make an imminent change expensive; design for known constraints.
  • Build stable domain concepts early, not hypothetical features.
  • Use experiments and measurements to replace guesses with evidence.

Relationships

YAGNI reinforces KISS and incremental delivery. It must be balanced with OCP when variation is already demonstrated.
