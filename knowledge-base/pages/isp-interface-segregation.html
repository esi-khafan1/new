ISP - Interface Segregation

Part 1: Foundationsprinciple

Definition

The Interface Segregation Principle says clients should not be forced to depend on operations they do not use. Interfaces should be shaped around client roles and capabilities, not around every operation a large implementation happens to support.

The goal is not to create hundreds of microscopic interfaces. It is to stop unrelated clients from sharing a release dependency and to make invalid operations impossible or unnecessary.

Problem It Solves

A Worker interface with work, eat, and sleep forces a Robot to implement meaningless methods. Consumers receive wide mocks, empty methods, and changes caused by features they never use.

C++ Before

struct Worker {
  virtual void work() = 0;
  virtual void eat() = 0;
  virtual void sleep() = 0;
};
class Robot : public Worker {
  void eat() override { /* meaningless */ }
  void sleep() override { /* meaningless */ }
};

C++ After

struct Workable { virtual ~Workable() = default; virtual void work() = 0; };
struct Eatable { virtual ~Eatable() = default; virtual void eat() = 0; };
class Robot : public Workable {
public: void work() override { /* do work */ }
};
class Human : public Workable, public Eatable {
public: void work() override {} void eat() override {}
};

Trade-offs and Misuse

  • Split when clients evolve independently or implementations leave methods unsupported.
  • Do not split merely to make interfaces short; coherent capability matters.
  • Keep interfaces stable and put vendor-specific detail behind adapters.

Relationships

ISP supports LSP by making contracts easier to honor, and supports DIP by giving high-level policy focused ports.
