Information Hiding

Part 1: Foundationsprinciple

Definition

Information hiding means a module conceals design decisions that are likely to change and exposes only the stable operations clients need. The boundary protects knowledge, not merely fields: algorithms, storage formats, synchronization, vendor APIs, and failure recovery can all be hidden.

Encapsulation is one mechanism for information hiding, but the principle also applies across modules, services, and packages. A good boundary prevents callers from depending on details that would make change expensive.

Problem It Solves

If callers know a database schema, cache layout, or retry algorithm, the hidden decision becomes a distributed dependency. One implementation change then requires edits and retesting across the system.

C++ Before

struct UserStore {
  std::unordered_map<int, User> cache;
  sqlite3* connection;
};
// Every caller manipulates storage details directly.

C++ After

class UserDirectory {
  class Impl;
  std::unique_ptr<Impl> impl;
public:
  UserDirectory();
  ~UserDirectory();
  std::optional<User> find(UserId id) const;
  void save(const User& user);
};
// Storage and cache decisions remain private.

Trade-offs and Misuse

  • Hiding everything can make debugging and performance behavior opaque.
  • Expose meaningful diagnostics and operational metrics without exposing representation.
  • Hide decisions likely to change, not facts every caller genuinely needs.

Relationships

Information hiding strengthens encapsulation, low coupling, SRP, and stable abstractions.
