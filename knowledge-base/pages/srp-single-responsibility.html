SRP - Single Responsibility

Part 1: Foundationsprinciple

Definition

The Single Responsibility Principle says a module should have one reason to change. A reason is a cohesive source of requirements, usually one stakeholder or business capability, not simply one method or one line of code.

SRP asks whether the code has one clear owner and one coherent purpose. A class may coordinate several calls and still obey SRP if coordination is its single responsibility; a tiny class can violate it by mixing domain rules, SQL, HTML, and email.

Problem It Solves

When unrelated responsibilities share a type, a change in persistence can break presentation, and a notification change can force domain tests to change. The result is high coupling, broad regression risk, and difficult tests.

C++ Before

class User { public:
  void validate();
  void saveToSql();
  std::string renderHtml() const;
  void sendWelcomeEmail();
};

C++ After

class User { /* state and domain rules */ };
class UserRepository { public: void save(const User&); };
class UserPage { public: std::string render(const User&) const; };
class Mailer { public: void sendWelcome(const User&); };

class RegisterUser {
  UserRepository& repo; Mailer& mailer;
public:
  void run(User user) { repo.save(user); mailer.sendWelcome(user); }
};

The coordinator owns registration workflow; each collaborator owns one reason to change.

Trade-offs and Misuse

  • Splitting every method into a class creates ceremony and indirection.
  • Use stakeholder-driven cohesion, not a rigid class-size rule.
  • Extract a responsibility when it has a distinct vocabulary, test seam, or change cadence.

Relationships

SRP supports high cohesion, low coupling, separation of concerns, and makes dependency inversion easier.
