DIP - Dependency Inversion

Part 1: Foundationsprinciple

Definition

The Dependency Inversion Principle says high-level policy should not depend directly on low-level details; both should depend on abstractions. Details such as SQL, HTTP, files, clocks, and frameworks should implement ports defined by the policy that needs them.

Dependency injection is a construction technique, not the principle itself. The important inversion is architectural: volatile infrastructure points inward toward stable business rules instead of controlling them.

Problem It Solves

When a use case constructs its database and clock, tests become slow and nondeterministic, migrations leak into policy, and replacing infrastructure requires editing business code.

C++ Before

class Billing {
public:
  void charge(int cents) {
    MySqlClient db;
    db.insert(cents);
  }
};

C++ After

struct Ledger {
  virtual ~Ledger() = default;
  virtual void record(int cents) = 0;
};
class Billing {
  Ledger& ledger;
public:
  explicit Billing(Ledger& l) : ledger(l) {}
  void charge(int cents) { ledger.record(cents); }
};

The composition root can provide a SQL adapter in production and an in-memory ledger in tests.

Trade-offs and Misuse

  • Do not create interfaces that merely mirror a vendor API.
  • Keep the port expressed in domain language.
  • Too much injection makes object construction noisy; compose at clear application boundaries.

Relationships

DIP reinforces SRP, ISP, OCP, ports-and-adapters, and testability.
